🎬 Comment utiliser ce guide

Ce guide reprend l'atelier Fluxym « Création d'un fichier structuré RFE » en deux temps : la partie 1 montre comment lire les annexes normatives et construire le fichier, la partie 2 comment le contrôler. Chaque module propose la vidéo, un parcours horodaté des étapes clés et la transcription complète.

💡

Une fois la méthode acquise, le Générateur UBL permet de produire directement un exemple conforme pour un cas d'usage donné, et la page Validation détaille les quatre niveaux de contrôle attendus par la réforme.

📄 Utiliser les fichiers de l'État

Comment constituer son fichier UBL, CII ou Factur-X à partir des ressources officielles de la DGFIP et de l'AFNOR. Niveau : débutant à intermédiaire.

Partie 1 — Les fichiers de l'État ~30 min🎯 Débutant
📝 Transcription complète — Partie 1

[0:00]Bonjour, on se voit aujourd'hui pour rentrer dans le détail de comment on crée sa facture électronique. Je partirai plus sur le format UBL, mais que vous vouliez faire du CII ou de la Factur-X, finalement, c'est à peu près la même manière de fonctionner. Premier élément, on va déjà suivre le site de la DGFIP des impôts.

[0:31]Tous les liens, on vous les fournira et vous y aurez accès au sein d'une page web qui récapitule l'ensemble des différents liens importants. Ici, quand vous descendez un petit peu, ce qui est intéressant, c'est de comprendre que c'est bien l'AFNOR qui détermine les règles.

[1:04]Ce qu'il faut comprendre, c'est qu'on vous parlera de Z12-12, Z12-13, Z12-14. La Z12-12, c'est le mode de fonctionnement de base de la facture électronique. C'est comment on la constitue.

[1:22]À l'intérieur de ce fichier-là, vous aurez les différents éléments à votre disposition : des exemples de factures, la norme telle qu'elle est. Ça vous fait une bonne lecture pour le soir, mais ce n'est pas vraiment là que vous allez travailler.

[1:41]La Z13, c'est pour la partie IT : comment on communique via API avec la plateforme agréée, les APIs SG5. La Z12-14, c'est plutôt les cas d'usage spécifiques.

[2:01]On va cliquer sur le fameux lien de l'AFNOR. On clique sur Consultation. Vous choisissez votre langue. Et vous ne cliquez pas sur « Téléchargement de la Norme », vous cliquez sur « Téléchargement des Annexes ».

[2:39]Ce qui nous intéresse, c'est le téléchargement des annexes. Il va vous télécharger la norme aussi.

[3:07]Important : les fichiers semblent avoir été créés sous Mac. Les titres sont très longs. Retirez un maximum de caractères du nom de dossier avant d'extraire, sinon vous aurez des erreurs sur Windows.

[4:27]Ne vous inquiétez pas des longueurs de noms dans les dossiers. Évitez juste au maximum d'avoir des longueurs trop importantes.

[4:49]Là, vous avez les éléments concernant la norme. Ça fait environ 91 pages. C'est en anglais malgré l'indication en français.

[5:41]Le fichier Excel important : ne prenez pas peur, il a une vingtaine d'onglets. À chaque fois que vous voulez travailler sur la norme, re-téléchargez le fichier car ça bouge.

[6:43]Onglet n°1 — Profil étendu : La norme de base, c'est l'EN 16931. Mais il est préférable de se baser directement sur l'UBL XML Extended. Pourquoi ? On connaît déjà les limites de l'EN 16931, et les évolutions vont tirer vers le profil étendu.

[7:36]Sur la facture classique, ça représente 3-4 champs de plus. Mais ça fait la différence : si demain on vous demande de vous replonger dedans 8-9 mois plus tard, ça ne sera pas plaisant.

[8:33]Onglet n°2 — Business Rules : Les règles métier. Par exemple, sur le flux 2, la BT23 dépend de la règle BRFR08. On retrouve ces règles dans l'onglet dédié.

[9:50]Pour certains champs (les BT), on doit aller voir des listes complètes de valeurs à respecter.

[10:41]Onglet n°3 — Codelist : Par exemple, ISO 4217 pour les devises. On fait Ctrl+F dans l'onglet Codelist pour retrouver la bonne liste. Le bleu ciel indique les valeurs les plus utilisées.

[12:34]Ce sont les trois principaux onglets : le profil étendu, les listes (Codelist) et les business rules.

[13:01]Ensuite, dans les annexes, la partie factures : plusieurs exemples de factures dans les trois formats (CII, Factur-X, UBL). C'est strictement la même facture dans les trois profils.

[13:53]La Factur-X, c'est un PDF lisible avec un fichier XML en pièce jointe qui comprend les informations sous format structuré.

[15:03]La méthode : Imprimez l'exemple de facture. Regardez sur votre facture à vous quels champs sont les mêmes. Retrouvez le mapping entre le PDF et le fichier XML structuré.

[15:46]Exemple : le numéro de facture sur le PDF se retrouve dans le fichier structuré sous la balise correspondante. En UBL, c'est des blocs CAC/CBC. En CII/Factur-X, c'est RSM/RAM.

[16:34]C'est toujours pareil : des blocs (BC), des sous-blocs, et des champs (CBC). C'est une hiérarchisation avec des niveaux (1 à 5).

[17:26]Dans le fichier Excel, chaque BT a un niveau et un XPath qui montre son arborescence dans le fichier XML.

[19:58]Certaines informations sont dans les attributs des balises (le « Schema ID »). C'est noté « @SchemeID » dans le fichier Excel.

[23:19]Les notes de facture (BT22) : il faut au moins 3 notes. On peut caractériser la typologie avec des codes entre dièses. Chaque code ne peut être utilisé qu'une seule fois.

[27:00]La BR-FR-20 : qualification du traitement attendu. On peut indiquer via une note quel traitement est attendu (B2C, international, plateforme agréée…). C'est utile pour le dispatching.

[27:38]L'objectif de cette vidéo : vous créer une boussole. Le plus important : regarder les règles (surtout flux 2), les notes d'usage, et le XPath pour l'arborescence.

[28:45]Prochaine étape → Vidéo Partie 2 pour aller plus loin avec les outils de validation IT.

🛠️ Outils IT & Validation

Comment tester et valider son fichier e-invoicing avec Visual Studio Code, les fichiers XSD et le Schématron. Niveau : avancé / IT.

Partie 2 — Outils IT & Validation ~30 min🎯 Avancé
📝 Transcription complète — Partie 2

[0:00]Bienvenue dans cette deuxième vidéo dédiée aux utilisateurs IT. L'objectif : tester le fichier une fois constitué et s'assurer qu'il correspond aux attendus de l'État.

[1:06]Pour tester, on utilise deux types de fichiers : le fichier XSD (pour valider la structure / le squelette) et le fichier SCH — Schématron (pour valider les règles de gestion de chaque champ).

[2:19]On va sur Visual Studio Code. Important : il y a le lien FNFE-MPE dans les ressources.

[2:43]Sur la page FNFE ressources, deux éléments à télécharger : le Schématron (le seul lien en rouge sur la page) et le fichier XSD UBL 2.1 (plus bas, section UBL 2.1).

[3:25]Pour le XSD : aller sur UBL 2.1 → XSD → Main Documentation → télécharger Invoice 2.1 et Credit Note 2.1 . Attention : il faut copier le contenu manuellement dans un fichier .xsd en supprimant la première ligne.

[5:22]Rappel : on repart des fichiers téléchargés dans la Partie 1 (site DGFIP, Z12-12, annexes AFNOR). On place les fichiers XSD et SCH au même niveau que notre facture d'exemple.

[6:23]Pour le Schématron : extraire le zip, prendre le fichier correspondant à votre format (UBL Extended dans notre cas), et le placer à côté de votre fichier de facture.

[8:38]Étape cruciale : il faut ajouter une ligne dans votre fichier XML de facture pour appeler le fichier SCH. Cette ligne doit être placée juste avant la balise <Invoice> .

[9:50]Extension 1 — XML Visual Editor v0.6.0 : permet de valider la structure avec le fichier XSD. Attention au mode « Restricted Mode » de VS Code qui peut bloquer les extensions.

[10:17]Pour voir l'éditeur XML : View → Appearance → Secondary Sidebar.

[11:17]Extension 2 — VS Code Lemmings Schematron : pour valider les règles de gestion. Prérequis : l'extension Red Hat XML (souvent installée par défaut) et Java 17+ sur votre machine.

[12:58]Pour vérifier Java : ouvrir le Terminal dans VS Code et taper java -version . Il faut au minimum la version 17.

[14:02]Validation XSD (structure) : ouvrir le fichier XML → extension XML Visual Editor → charger le fichier XSD → « Check well-formedness » puis « Validate with schema ». Le mode grille permet de visualiser l'arborescence.

[17:24]Les erreurs structurelles s'affichent en rouge directement dans le fichier. Exemple : « Has no child element » signifie un attribut mal placé.

[20:18]Pour chaque erreur, retourner dans le fichier Excel pour vérifier les attributs autorisés (ex: BT-18 → @SchemeID → liste UNTDID 1153).

[23:44]Validation Schématron (règles métier) : les erreurs apparaissent dans View → Problems. Le Schématron vérifie les valeurs des champs, pas seulement la structure.

[25:08]Exemple : BT-1 (numéro de facture) → max 35 caractères, seuls les alphanumériques et + - _ / autorisés. Si vous mettez une étoile *, l'erreur s'affiche instantanément en français.

[26:19]Autre exemple : une date mal formatée → erreur immédiate. Un taux de TVA > 100% → erreur immédiate. C'est du feedback en temps réel.

[27:17]La méthode complète : 1) Constituer le fichier avec la Partie 1. 2) Valider la structure avec XSD + XML Visual Editor. 3) Valider les valeurs avec SCH + Schématron. 4) Itérer sur vos cas d'usage.

[29:01]Pour la suite : analyser vos cas d'usage spécifiques. Chaque cas d'usage détermine quels BT/BG sont nécessaires. Faites-vous accompagner pour cette étape.

⚙️ Prérequis techniques

À installer sur le poste avant de suivre la partie 2.

  • Visual Studio Code — Environnement de développement (gratuit)
  • Java 17+ — Vérifier avec java -version dans le terminal
  • Extension XML Visual Editor v0.6.0 — Pour la validation de structure XSD
  • Extension Red Hat XML — Souvent pré-installée, nécessaire pour Schematron
  • Extension VS Code Lemmings Schematron — Pour la validation des règles métier
  • Fichier XSD — Invoice 2.1 (et Credit Note 2.1) depuis FNFE / UBL 2.1
  • Fichier SCH — Schématron UBL Extended depuis FNFE ressources
  • Désactiver le Restricted Mode de VS Code si les extensions sont bloquées
